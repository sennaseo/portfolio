① 에너지 다이어그램 통합 모델: 어댑터 한 겹으로 무수정 이관

전력 계통도와 변환 토폴로지가 서로 다른 데이터 구조여서 화면마다 따로 다뤄야 했습니다. 두 구조를 하나의 데이터 모델로 통합하고, 기존 화면과 새 모델 사이에 어댑터 계층을 한 겹 두었습니다.

결과: UI 파일 33개를 수정하지 않고 신규 API로 이관, 테스트 368건 통과. 리스크가 큰 전환일수록 경계를 한 겹 두는 쪽이 싸다고 판단했습니다.

② 센서 132개 중 97개만 보이던 문제: 화면 밖까지 추적

화면 코드만 봐서는 원인이 나오지 않았습니다. API 응답과 필터 로직을 단계별로 되짚어 원인을 찾았고, 계통도에 등록되지 않은 센서 35개를 발견해 백엔드에 등록을 요청했습니다. 결과적으로 센서 전량이 노출됐습니다.

③ 소비 전력량 과다 집계: 말 대신 실측으로

소비 전력량이 실제보다 크게 집계되는 이상을 실측값과 대조해, 누적 전력량 카운터 점프가 원인임을 규명하고 백엔드에 전달했습니다. 논의가 "누구 잘못인가"에서 "어떻게 처리할까"로 넘어갔습니다.

그 밖에 한 일

  • 에너지 사용량 모니터링·분석 화면 설계와 구현 전체, 부서 마스터·요금분배표 화면 신설
  • 공통 컴포넌트 FilterChipBar FilterPanel NumericTable 신설. 필요를 실제로 세어 본 뒤 도입하고 과도한 공통화는 보류
  • 표 컬럼폭 흔들림을 table-fixed + colgroup으로 근본 해결, localStorage 필터 영구 저장으로 첫 화면이 잘못 뜨던 버그 수정
  • 프론트엔드 오픈소스 라이선스 목록(SBOM) 작성

① 입력 흐름을 워크스페이스 구조로 재설계 (기획 주도)

ESG·CBAM·PCF 입력 항목이 과다하고 흐름이 흩어져 기업 고객이 어디서 무엇을 입력할지 헤맸습니다. MRV 사업으로 5개 제조기업 현장에서 데이터 수집과 보고서 제작에 참여하며 실제 입력 과정을 관찰했고, 그 관찰을 근거로 워크스페이스 기반 구조로 재설계하는 기획을 주도했습니다.

① 렌더링 전략을 화면별로 판단

Next.js 15 App Router에서 화면마다 SSR과 CSR을 판단해 적용했습니다. "Next.js를 써 봤다"가 아니라 "렌더링 전략을 골랐다"가 제가 말할 수 있는 부분입니다.

② 분석 대기 UX: 어느 화면에 있든 완료 알림

분석이 오래 걸리는 동안 사용자가 다른 화면을 쓸 수 있도록 localStorage + BroadcastChannel로 분석 상태를 탭 간에 전파했습니다. 어느 화면에 있든 완료 토스트를 받습니다.

③ 모바일 전용 PWA

440px 모바일 전용 PWA로 만들고, React Three Fiber로 3D 마스코트를 넣었습니다.

05 · AI 활용 능력

AI를 쓰되, 결과는 검증합니다

Claude Code를 개발 도구로 쓰고, 산출물의 책임은 제가 집니다.

① csStudy: Claude Code로 만들어 Google Play 출시 절차까지

CS·React·TypeScript·Java·Spring 면접 대비 퀴즈 앱입니다. 웹 PWA, 안드로이드 앱, 홈화면 위젯까지 만들었고 Google Play 스토어 출시 절차까지 진행했습니다. 모든 코드 주석과 해설은 "비유 먼저, 쉬운 말, 전문용어는 괄호" 원칙으로 쓰고, 듀오링고식 게임화(수집·진화·보상) UI를 적용했습니다.

② 도구는 AI, 책임은 사람

csStudy는 Claude Code로 만들었지만, 출시까지 가는 동안 결과를 그대로 쓰지 않고 직접 확인했습니다. 실무의 데이터 검증(클링커 ÷100 누락, 전력량 카운터 점프)은 AI 없이 계산식과 실측값을 직접 대조해 찾아냈습니다. AI는 속도를 올리는 도구이고, 숫자의 정확성은 제가 확인합니다.
